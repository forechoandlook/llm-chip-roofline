# 算力配比结论（Qwen3.8-27B · NVFP4）

## 问题到底在问什么

不是「1:8 和 1:16 哪个数字更好」。

在 **不算面积、不算功耗** 的前提下，核心是：

> **Vector（以及 SRAM / 能否与 Cube 同拍）配到什么程度，才不会拖慢 Cube？**

Decode 则是另一堵墙：**会不会拖慢的是 HBM，不是 Cube。**

负载默认：Prefill seq 8K × batch 4（四条独立 8K，不是一条 32K）；Decode batch 4、context 8K。精度 NVFP4。模型 64 层 = 48 GDN + 16 Gated Attention。

---

## 直接结论（当前模拟、不考虑面积）

| 阶段 | 墙在哪 | 改 Cube:Vector 有没有用 |
|---|---|---|
| Prefill | **Cube（GEMM）** | 8:1～16:1 几乎没有。Vector 盖不住 Cube。 |
| Decode（NVFP4 / FP8） | **带宽（搬权重）** | 几乎没有。Cube 经常在等 HBM。 |
| Decode（W4BF16） | 16:1 前带宽；之后 **W4 反量化 Vector** | 16:1 往后 tok/s 会掉。 |

所以：**不考虑面积时，8:1～16:1 对 Prefill 无所谓**——Cube 已经是墙。Decode 在 NVFP4/FP8 下也几乎不看 Vector。**W4BF16 除外**：本页把每颗权重算 3 FLOP Vector 反量化（\(3KN\)，与 token 数 \(M\) 无关），Decode \(M=4\) 时 \(T_V/T_C \approx 1.5/M \times\) Cube:Vector \(=0.375\times\) 比例。自定义点上 8:1 仍是带宽墙（~1800 tok/s），16:1 Vector 已经贴上带宽（~1700），32:1 变成 Vector 墙（~1210），64:1 ~693。折线 16:1 往后掉，掉的是 **dequant，不是 softmax/RMS**。

折线图默认 **固定 Cube BF16**，只拧 Vector。NVFP4 下这条线几乎是平的，原因在计时模型：

每个算子 \(T_\text{算力}=\max(C,V)+\gamma\min\)，再 \(T=\max(T_\text{算力},T_\text{带宽})+\alpha\min\)，端到端是各算子 \(T\) 相加。

- Prefill：时间几乎全在带权 GEMM。Cube FLOP 是 \(2MKN\)，Vector 只是 epilogue / scale+cast（大约 \(1/N\)）。\(C\gg V\)，于是 \(T_\text{算力}\approx T_\text{Cube}\)。Cube 峰值固定，Prefill ms 就不随 Cube:Vector 动。
- Decode（NVFP4/FP8）：每步把权重从 HBM 再搬一遍，\(T_\text{带宽}\gg T_\text{算力}\)，\(T\approx T_\text{带宽}\)。
- Decode（W4BF16）：\(T_V=3KN/\text{Vector峰值}\) 随比例线性涨，16:1 之后超过 \(T_\text{带宽}\)。

线要翘，NVFP4 得把 Vector 砍到 GDN / softmax / SiLU 盖过 Cube；W4BF16 Decode 在 16:1 就会翘。总量守恒去扫会减 Cube，Prefill 变慢是 GEMM 峰值掉了。

---

## 什么情况下会拖慢 Cube

Cube 被拖慢，只有 Vector（或访存）变成 **和 Cube 抢时间** 的那段：

1. **从 Cube 峰值里匀走算力给 Vector**。Cube 下降，Prefill GEMM 变慢。本页默认扫不做这件事。
2. **Cube 与 Vector 不能同拍**（昇腾类 tile 上 \(C+V\)），且 Decode / 小 \(N\) 时 Vector 段进求和。GPU + 大 Prefill 时 tile 多，稳态仍是 \(\max(C,V)\)，GEMM 的 Vector 大约只有 \(1/N\)，拖不动。
3. **GDN 状态衰减走 FP32 Vector**（没有 FP32 Cube）。Vector/FP32 砍过头，`gdn_delta_rule` 变慢，叠在 Prefill 墙上。
4. **SRAM 太小**：tile 切碎、权重不能驻片、激活回 HBM，DMA 和 Cube 串起来，看起来像算力配比问题，其实是片上容量。

反过来说：**不会拖慢 Cube 的配比**，就是 Vector 足够覆盖这些「Cube 盖不住」的活（GDN FP32 衰减、softmax、SiLU/RMS、NVFP4 激活 scale+cast），同时 **不要用减 Cube 的方式去加 Vector**。

对本负载，常见的 1:8～1:16（Cube:Vector，BF16）都还在「Vector 拖不动 Cube」一侧。要拖到 Cube，得把 Vector 砍到 GDN/epilogue 变成墙，或从 Cube 面积里匀走。

## 两套模拟各自回答什么

**本仓库（配比实验室，`serve.mjs`）**  
解析 Roofline：算子 FLOP/搬运 → \(T=\max(T_\text{算力},T_\text{带宽})+\alpha\min\)，算力侧 \(T_\text{算力}=\max(C,V)+\gamma\min\)。适合对账公式、看墙在 Cube 还是 HBM。**只拧比例没有物理意义**，因为没面积、没 tile 段、没 SRAM 驻留。

**chip-simulator（`/Users/wangyangzuo/tmp/chip-simulator`）**  
五段 tile 流水 \(T=(N-1)\max(\text{段})+\sum\text{段}\)；`overlap.cubeVector`；SRAM 限制 tile / 权重驻留；NVFP4 权重 MatMul：激活 BF16 搬运、global scale 已有、Vector `2MK`、Cube FP4；FA 仍是 BF16 Cube + softmax FP32；GDN 为 Cube BF16 \(6MD^2\) + Vector FP32 \(2MD^2\)。

它能把「某一段卡在 DMA / Cube / Vector」拆开，**不会推翻**「Prefill≈Cube、Decode≈带宽」。只是在 Decode、小 batch、不同拍、SRAM 很紧时，Vector 会比配比页更显眼。

## chip-simulator 对照（固定 Cube BF16，扫 Vector）

芯片：H100 规格表 Cube BF16 = 495 T，HBM 不动。模型 Qwen3.8-27B NVFP4。Prefill B=4 S=8192（`maxBatchedTokens=32768`，整段 prefill，不是默认 16 token chunk）。Decode B=4 C=8192。KPI 来自 schedule-trace。

两种同拍：

- **gpu-parallel**：`overlap.cubeVector=true`。FlashAttention 仍 \(\max(C,V)\)；GDN `linear-attn` 引擎里写死 \(C+V\)。
- **lockstep-gemm**：`overlap.cubeVector=false`。GEMM 按 \(C+V\)；FA 仍按算子覆盖走并行；片上 issue 对 Cube/Vector 加排他锁。

| Cube:Vector | Vector T | Prefill ms 同拍 | Prefill ms 不同拍 | Decode tok/s 同拍 | Decode tok/s 不同拍 |
|---|---|---|---|---|---|
| 2:1 | 247.5 | 2845（Cube 94.7%） | 5337（Cube 94.7%） | 359 | 343 |
| 4:1 | 123.8 | 2964 | 5460 | 334 | 294 |
| 8:1 | 61.9 | 3195（Cube 91%） | 5699 | 252 | 221 |
| 16:1 | 30.9 | 3663（GDN 变 Vector 墙） | 6185 | 160 | 147 |
| 32:1 | 15.5 | 4734 | 7301 | 86 | 82 |
| 64:1 | 7.7 | 6289（Cube 75% / Vector 20%） | 8904 | 52 | 51 |

组成上发生了什么：

**Prefill，固定 Cube。** 大头仍是 FA Cube + FFN Cube。FFN 的 Vector FLOP 大约是 Cube 的 \(1/N\)，所以 **同一条 GEMM 的 cost 流水几乎不随比例动**（gate 约 7.87 ms，2:1 和 64:1 一样）。比例变慢，是因为 **GDN 永远 \(C+V\)**：16:1 起 `LinearAttention` 被标成 vector-bound，64:1 它变成 Prefill 第一名（~10.3 ms/层量级的 trace 份额），Vector 时间份额从 0 升到约 20%。同拍线下 2:1→8:1 只慢约 12%；砍到 16:1 以后才明显。

**不同拍把 Prefill 整体抬了约 1.8×**（2:1：2845 vs 5337）。GEMM 的 cost 段几乎没加（gate 7.869 → 7.872 ms），多出来的时间在 **schedule-trace 的 Cube/Vector 排他 issue**，不是 tile 公式里把 \(V\) 加进 \(C\)。FA 算子覆盖仍是并行，所以这条 1.8× 是芯片级 XOR，不是「每条 GEMM 变成 \(C+V\)」。

**Decode。** FA 钉在 dma-in（KV）。2:1～4:1 时一层里 launch（2.5 µs/op）+ dma-in 占 60–70%，Vector 份额 0。从 **8:1** 起 FFN gate/up/down 被标成 vector-bound：Decode 的 M=4，NVFP4 激活 scale+cast 的 Vector FLOP 相对 Cube 不再是 \(1/N\)（本 run 里 gate 约 189 M Vector vs 713 M Cube），小 tile 的 \(\sum\) 段又藏不住。再砍 Vector，tok/s 从 ~350 掉到 ~50。配比页 Decode 几乎水平，是因为那边把 GEMM Vector 当成 \(1/N\)、又没有 per-op launch、带宽用 max 盖住。

对照结论：chip-simulator **没有推翻 Prefill≈Cube**（8:1 时 Cube 仍约 91%）。它说明两件配比页看不见的事——GDN 串行会在 Vector 偏瘦时先露头；Decode 小 M + NVFP4 激活 Vector + launch 会让 8:1 就开始掉 tok/s。不同拍主要是 issue 锁把 Prefill 抬高一截，不是 GEMM 公式从 \(\max\) 变成 \(C+V\)。

### FlashAttention / RMSNorm 的 Vector 去哪了

Qwen3.8-27B `head_dim=256`。FA 公式是 Cube \(4\cdot m\cdot C\cdot D\cdot H\)（QKᵀ+PV）、Vector softmax \(6\cdot m\cdot C\cdot H\)。FLOP 比 \(V/C=6/(4D)=0.0059\)。同拍走 \(\max(C,V)\)，8:1 时 Vector 时间大约是 Cube 的 \(0.0059\times 8\approx 5\%\)，藏在 Cube 里；扫到 64:1 也还是 FA cube-bound，墙时间钉在 8.89 ms（代表层）。softmax 的 FLOP 不少（分数个数 ×6），相对 MMA（每个分数 \(4D=1024\)）仍然薄。

RMS / SwiGLU / Residual / RoPE 都在图里，而且是纯 Vector。Prefill 代表层上它们加起来大约 4–5% 墙时间，**几乎全是 dma-in**：强度大约 3 FLOP/byte，远低于 Vector ridge。8:1 时 RMS 的 Vector 段 ~22 µs、搬运 ~435 µs；64:1 时 Vector 段涨到 ~174 µs，仍低于搬运。所以「算子个数很多」不等于「Vector 峰值成为墙」。

### FP8 和 W4A16（同一套固定 Cube 扫）

FA 仍按 BF16 MMA + softmax FP32，三种精度 FA 墙时间相同。变的是投影 GEMM 的 Cube 峰值、权重字节、以及 Vector 税。

| 精度 | Prefill 代表层主墙 | RMS+Swi+Res | Decode 主墙 | Vector 何时露头 |
|---|---|---|---|---|
| NVFP4 | FFN Cube 55% + FA Cube 21% | ~4%，dma-in | FFN 激活 scale+cast（8:1 起 vector）+ FA dma-in | Prefill：GDN 16:1；Decode：FFN 8:1 |
| FP8 | FFN Cube 59% + FA Cube 22%（Cube 走 FP8 990T，墙更矮） | ~2%，dma-in（激活 1B） | FFN **dma-in ~78%**（无 dequant Vector） | Prefill 仍是 GDN；Decode 比例几乎不动 |
| W4A16 | FFN Cube 66%（Cube 走 FP16 495T，约 2× FP8） | ~3%，dma-in | launch + FA dma-in；权重 INT4 搬运更少 | Prefill 仍是 GDN；W4 dequant 是 \(2\cdot KN\)，Prefill \(1/M\) 可忽略 |

FP8 把投影变快、激活变窄，RMS 更不容易碰到 Vector 墙（64:1 才刚贴上）。W4A16 把 Decode 的权重搬运砍掉，tok/s 比 NVFP4/FP8 高，但 Prefill 更吃 BF16 Cube。三种精度里，**会随 Cube:Vector 明显变慢的仍然是 GDN 的 \(C+V\)**，不是 FA softmax，也不是 RMSNorm。

## NVFP4 / Attention（建模口径）

- **带权重的 MatMul**：激活按 BF16 读；权重 W4 + 每 16 个数一个 FP8 scale；激活 global scale 已有（不做 amax）；Vector 只做 scale+cast；Cube 原生 FP4。
- **FlashAttention**：QKᵀ、PV 为 BF16 Cube；softmax FP32 Vector；不走 FP4。
- **GDN delta rule**：矩阵更新 BF16 Cube；状态衰减 FP32 Vector（无 FP32 Cube）；状态按 FP32 搬。

## 还答不出的

同等 **面积或功耗** 下，1 mm² 换成 Cube、Vector 还是 HBM 哪个更值。没有这笔账，就不能说「最好的配比」。下一步若要一个数，应在 chip-simulator 里固定面积（或功耗），扫 PE 几何 × SRAM × HBM × 能否同拍，看 Prefill ms 与 Decode tok/s 的帕累托。
