# 算力配比结论（Qwen3.8-27B · NVFP4）

## 问题到底在问什么

不是「1:8 和 1:16 哪个数字更好」。

在 **不算面积、不算功耗** 的前提下，核心是：

> **Vector（以及 SRAM / 能否与 Cube 同拍）配到什么程度，才不会拖慢 Cube？**

Decode 则是另一堵墙：**会不会拖慢的是 HBM，不是 Cube。**

负载默认：Prefill seq 8K × batch 4（四条独立 8K，不是一条 32K）；Decode batch 4、context 8K。精度 NVFP4。模型 64 层 = 48 GDN + 16 Gated Attention。

---

## 直接结论（当前模拟、不考虑面积）

| 阶段 | 墙在哪 | 改 Cube:Vector 有没有用 |
|---|---|---|
| Prefill | **Cube（GEMM）** | 8:1～16:1 几乎没有。再瘦到 32:1 起 GDN 衰减和 FA softmax 会变成 Vector 墙。 |
| Decode（NVFP4 / MXFP8） | **带宽（搬权重）** | 几乎没有。Cube 经常在等 HBM。 |
| Decode（W4BF16） | 16:1 前带宽；之后 **W4 反量化 Vector** | 16:1 往后 tok/s 会掉。 |

GEMM 拆成：先 FP32 量化 → FP4/FP8 MatMul → 输出 FP32，再乘张量级 \(s_\text{global}\)（MN，FP32 Vector）。块 scale 仍在 Tensor Core，**不是** \(MN\cdot(K/g)\)。这条 Vector 仍是 \(O(MK+MN)\)，盖不住 \(2MKN\)，所以 **Prefill / Decode 墙相对上一版没有变**。

折线图默认 **固定 Cube BF16**，只拧 Vector。每个算子 \(T_\text{算力}=\max(C,V)+\gamma\min\)，再 \(T=\max(T_\text{算力},T_\text{带宽})+\alpha\min\)。

- Prefill：时间几乎全在带权 GEMM。Cube \(2MKN\)。块 scale 在 Tensor Core。动态量化 + 输出 FP32 + \(s_\text{global}\) 乘 MN 走 FP32 Vector。
- Decode（NVFP4/MXFP8）：每步把权重从 HBM 再搬一遍，\(T_\text{带宽}\gg T_\text{算力}\)。
- Decode（W4BF16）：\(T_V=3KN/\text{Vector峰值}\) 随比例线性涨，16:1 之后超过 \(T_\text{带宽}\)。

---

## 什么情况下会拖慢 Cube

Cube 被拖慢，只有 Vector（或访存）变成 **和 Cube 抢时间** 的那段：

1. **从 Cube 峰值里匀走算力给 Vector**。Cube 下降，Prefill GEMM 变慢。本页默认扫不做这件事。
2. **Cube 与 Vector 不能同拍**（昇腾类 tile 上 \(C+V\)），且 Decode / 小 \(N\) 时 Vector 段进求和。GPU + 大 Prefill 时 tile 多，稳态仍是 \(\max(C,V)\)。NVFP4 的 \(s_\text{global}\) 乘是 \(MN\)，拖不动 Cube。
3. **GDN 状态衰减走 FP32 Vector**（没有 FP32 Cube）。Vector/FP32 砍过头，`gdn_delta_rule` 变慢，叠在 Prefill 墙上。
4. **SRAM 太小**：tile 切碎、权重不能驻片、激活回 HBM，DMA 和 Cube 串起来，看起来像算力配比问题，其实是片上容量。

反过来说：**不会拖慢 Cube 的配比**，就是 Vector / FP32 足够覆盖这些「Cube 盖不住」的活（GDN FP32 衰减、softmax、SiLU/RMS、NVFP4 动态量化），同时 **不要用减 Cube 的方式去加 Vector**。

对本负载，常见的 1:8～1:16（Cube:Vector，BF16）都还在「Vector 拖不动 Cube」一侧。要拖到 Cube，得把 Vector 砍到 GDN/epilogue 变成墙，或从 Cube 面积里匀走。

## 两套模拟各自回答什么

**本仓库（配比实验室，`serve.mjs`）**  
解析 Roofline：算子 FLOP/搬运 → \(T=\max(T_\text{算力},T_\text{带宽})+\alpha\min\)，算力侧 \(T_\text{算力}=\max(C,V)+\gamma\min\)。适合对账公式、看墙在 Cube 还是 HBM。**只拧比例没有物理意义**，因为没面积、没 tile 段、没 SRAM 驻留。

**chip-simulator（`/Users/wangyangzuo/tmp/chip-simulator`）**  
五段 tile 流水 \(T=(N-1)\max(\text{段})+\sum\text{段}\)；`overlap.cubeVector`；SRAM 限制 tile / 权重驻留；NVFP4/MXFP8 权重 MatMul：激活 BF16 搬运，先 FP32 量化，Cube 走 FP4/FP8，输出 FP32，NVFP4 的 \(s_\text{global}\) 乘 \(MN\) 走 FP32 Vector，块 scale 在 Tensor Core；FA 的 KV 是 BF16，QKᵀ/PV 是 BF16 Cube，softmax / P 写出 / O 累加走 FP32 Vector；RMS / SiLU / 残差按 BF16 搬运。GDN 为 Cube BF16 \(6MD^2\) + Vector FP32 \(2MD^2\)。

它能把「某一段卡在 DMA / Cube / Vector」拆开，**不会推翻**「Prefill≈Cube、Decode≈带宽」。只是在 Decode、小 batch、不同拍、SRAM 很紧时，Vector 会比配比页更显眼。

## chip-simulator 对照（固定 Cube BF16，扫 Vector）

芯片：H100 规格表 Cube BF16 = 495 T，HBM 不动。模型 Qwen3.8-27B NVFP4。Prefill B=4 S=8192（`maxBatchedTokens=32768`，整段 prefill，不是默认 16 token chunk）。Decode B=4 C=8192。KPI 来自 schedule-trace。

两种同拍：

- **gpu-parallel**：`overlap.cubeVector=true`。FlashAttention 仍 \(\max(C,V)\)；GDN `linear-attn` 引擎里写死 \(C+V\)。
- **lockstep-gemm**：`overlap.cubeVector=false`。GEMM 按 \(C+V\)；FA 仍按算子覆盖走并行；片上 issue 对 Cube/Vector 加排他锁。

| Cube:Vector | Vector T | Prefill ms 同拍 | Prefill ms 不同拍 | Decode tok/s 同拍 | Decode tok/s 不同拍 |
|---|---|---|---|---|---|
| 2:1 | 247.5 | 2845（Cube 94.7%） | 5337（Cube 94.7%） | 359 | 343 |
| 4:1 | 123.8 | 2964 | 5460 | 334 | 294 |
| 8:1 | 61.9 | 3195（Cube 91%） | 5699 | 252 | 221 |
| 16:1 | 30.9 | 3663（GDN 变 Vector 墙） | 6185 | 160 | 147 |
| 32:1 | 15.5 | 4734 | 7301 | 86 | 82 |
| 64:1 | 7.7 | 6289（Cube 75% / Vector 20%） | 8904 | 52 | 51 |

组成上发生了什么：

**Prefill，固定 Cube。** 大头仍是 FA Cube + FFN Cube。下面这列数字来自 **旧的 BF16 \(2MK\) 记账**（当时把 global scale 当成已知，Vector 只做 scale+cast）。那一版 FFN Vector FLOP 大约是 Cube 的 \(1/N\)，所以 **同一条 GEMM 的 cost 流水几乎不随比例动**（gate 约 7.87 ms，2:1 和 64:1 一样）。改成 FP32 动态量化之后，配比页上 B300 的 \(T_V/T_C\) 从大约 2% 升到大约 5%，墙还是 Cube。比例变慢，是因为 **GDN 永远 \(C+V\)**：16:1 起 `LinearAttention` 被标成 vector-bound，64:1 它变成 Prefill 第一名（~10.3 ms/层量级的 trace 份额），Vector 时间份额从 0 升到约 20%。同拍线下 2:1→8:1 只慢约 12%；砍到 16:1 以后才明显。

**不同拍把 Prefill 整体抬了约 1.8×**（2:1：2845 vs 5337）。GEMM 的 cost 段几乎没加（gate 7.869 → 7.872 ms），多出来的时间在 **schedule-trace 的 Cube/Vector 排他 issue**，不是 tile 公式里把 \(V\) 加进 \(C\)。FA 算子覆盖仍是并行，所以这条 1.8× 是芯片级 XOR，不是「每条 GEMM 变成 \(C+V\)」。

**Decode。** FA 钉在 dma-in（KV）。2:1～4:1 时一层里 launch（2.5 µs/op）+ dma-in 占 60–70%，Vector 份额 0。从 **8:1** 起 FFN gate/up/down 被标成 vector-bound。这是 **旧 \(2MK\) run**：Decode \(M=4\) 时 gate 约 189 M Vector vs 713 M Cube，小 tile 的 \(\sum\) 段藏不住，tok/s 从 ~350 掉到 ~50。现行模型把动态量化改成 FP32 之后，配比页上同一条 gate 的 \(T_V/T_C\) 仍约 0.05，Decode 的带宽时间大约是 Vector 的两千倍，线还是平的。chip-simulator 这列还没按新 FLOP 重扫；配比页水平，是因为没有 per-op launch、带宽用 max 盖住，不是因为量化可以忽略不计。

对照结论：chip-simulator **没有推翻 Prefill≈Cube**（8:1 时 Cube 仍约 91%）。它说明两件配比页看不见的事——GDN 串行会在 Vector 偏瘦时先露头；Decode 小 M + NVFP4 激活 Vector + launch 会让 8:1 就开始掉 tok/s。不同拍主要是 issue 锁把 Prefill 抬高一截，不是 GEMM 公式从 \(\max\) 变成 \(C+V\)。

### FlashAttention / RMSNorm 的 Vector 去哪了

Qwen3.8-27B `head_dim=256`。FA 公式是 Cube \(4\cdot m\cdot C\cdot D\cdot H\)（QKᵀ+PV）、Vector softmax \(6\cdot m\cdot C\cdot H\)。FLOP 比 \(V/C=6/(4D)=0.0059\)。同拍走 \(\max(C,V)\)，8:1 时 Vector 时间大约是 Cube 的 \(0.0059\times 8\approx 5\%\)，藏在 Cube 里；扫到 64:1 也还是 FA cube-bound，墙时间钉在 8.89 ms（代表层）。softmax 的 FLOP 不少（分数个数 ×6），相对 MMA（每个分数 \(4D=1024\)）仍然薄。

RMS / SwiGLU / Residual / RoPE 都在图里，而且是纯 Vector。Prefill 代表层上它们加起来大约 4–5% 墙时间，**几乎全是 dma-in**：强度大约 3 FLOP/byte，远低于 Vector ridge。8:1 时 RMS 的 Vector 段 ~22 µs、搬运 ~435 µs；64:1 时 Vector 段涨到 ~174 µs，仍低于搬运。所以「算子个数很多」不等于「Vector 峰值成为墙」。

### FP8 和 W4A16（同一套固定 Cube 扫）

FA 仍按 BF16 MMA + softmax FP32，三种精度 FA 墙时间相同。变的是投影 GEMM 的 Cube 峰值、权重字节、以及 Vector 税。

| 精度 | Prefill 代表层主墙 | RMS+Swi+Res | Decode 主墙 | Vector 何时露头 |
|---|---|---|---|---|
| NVFP4 | FFN Cube 55% + FA Cube 21% | ~4%，dma-in | 旧 \(2MK\) run：FFN 激活 Vector（8:1 起）+ FA dma-in。新 FP32 量化在配比页上仍约 Cube 的 5%，Decode 仍是带宽 | Prefill：GDN 16:1；Decode 的 8:1 是旧 \(2MK\) run |
| FP8 | FFN Cube 59% + FA Cube 22%（Cube 走 FP8 990T，墙更矮） | ~2%，dma-in（激活 1B） | FFN **dma-in ~78%**（无 dequant Vector） | Prefill 仍是 GDN；Decode 比例几乎不动 |
| W4A16 | FFN Cube 66%（Cube 走 FP16 495T，约 2× FP8） | ~3%，dma-in | launch + FA dma-in；权重 INT4 搬运更少 | Prefill 仍是 GDN；W4 dequant 是 \(2\cdot KN\)，Prefill \(1/M\) 可忽略 |

FP8 把投影变快、激活变窄，RMS 更不容易碰到 Vector 墙（64:1 才刚贴上）。W4A16 把 Decode 的权重搬运砍掉，tok/s 比 NVFP4/FP8 高，但 Prefill 更吃 BF16 Cube。三种精度里，**会随 Cube:Vector 明显变慢的仍然是 GDN 的 \(C+V\)**，不是 FA softmax，也不是 RMSNorm。

## NVFP4 / Attention（建模口径）

- **带权重的 MatMul**：对齐 SGLang Qwen3.8-NVFP4 / RadixArk：只有 FFN 走页面精度（NVFP4 W4A4 或 MXFP8）。GDN 的 `in_qkv` / `in_z` / `out` 走 FP8；`in_proj_ba`（衰减/写入门）留 BF16。复发核 BF16 Cube + FP32 衰减。
- **QKVO**：q / k / v / o / attn_gate 五个投影固定 BF16 Cube。KV cache 固定 BF16。
- **FlashAttention**：KV 是 BF16。QKᵀ、PV 为 BF16 Cube。online softmax 走 FP32 Vector。
- **GDN delta rule**：矩阵更新 BF16 Cube；状态衰减 FP32 Vector（无 FP32 Cube）；状态按 FP32 搬。

## 核对：Ascend 910，以及这页结论还站不站得住

飞书原文这次打不开（wiki 返回 404，需要登录）。下面只核对本仓库这页结论，以及芯片表里的峰值。

**Ascend 910 不是 910B。** 2019 年的 910A 是 32 个 Da Vinci 核、Cube FP16 **256T**、HBM2 **32GB / 1.2 TB/s**、功耗 **310W**。Vector 与 Cube 在同一个 AI Core 里，IEEE 写标量、向量、矩阵可以同时干。按达芬奇 2048-bit 向量、1 GHz：FP16 FMA **8.19T**，FP32 FMA **4.10T**，FP32 纯加（AXPY）**2.05T**。论文表上的「910A Vector FP32 AXPY = 2T」对得上，所以 Cube:Vector（FP16）大约是 **31:1**，不是 910B2 的 16:1，也不是营销口里的「256T 已经含向量」。CSET 写过：对外的 256T 没把向量算进去；更高的一档 SKU 可以到大约 320T。

910B2 仍按 24 个 Cube + 48 个 Vector、1.8 GHz：**353.9T / 22.1T = 16:1**。这是 B2，不是全系列。另一档公开数是 20 Cube + 40 Vector、Cube 294.9T。910B 把 Cube 核和 Vector 核拆开，数据经 L2/HBM 交换，所以「昇腾不能同拍」说的是 **910B 这一代**。910A 的论文口径是核内可并行。910C 双 die、每 die 约 376–379T，封装 **752T** 仍然成立；800T 是营销档。

**结论里站得住的部分**

- Prefill 的大头是 GEMM Cube。B300、Qwen3.8-27B 的 FFN gate（\(K=5120, N=17408\)）：Prefill \(M=32768\) 时 NVFP4 \(T_C=433\,\mu\text{s}\)、\(T_V=34.3\,\mu\text{s}\)、\(T_\text{带宽}=191\,\mu\text{s}\)，\(T_V/T_C=0.079\)。整段 Prefill 约 220 ms，Cube 份额约 0.66。MXFP8 同一条 gate \(T_V/T_C=0.020\)。
- Decode 在 NVFP4/MXFP8、权重每步从 HBM 再读一遍时，主墙是带宽。同一条 NVFP4 gate、\(M=4\)：\(T_V/T_C\) 仍是 0.079，\(T_\text{带宽}=6.29\,\mu\text{s}\)。端到端约 2.05 ms，带宽份额约 1.00。
- W4BF16 的反量化 Vector 与 token 数无关。Decode M 很小以后，16:1 往后会从带宽墙换成 Vector 墙。这个方向对。
- 「还不能在同等面积下选出一个最好的比例」仍然对。新芯片只是把脊点抬高，没有给出面积交换。

**需要改口的部分**

- 「常见 1:8～1:16 都还拖不动 Cube」只覆盖表里原来那些 GPU。**910A 已经在 31:1**。GDN 的 FP32 衰减没有 FP32 Cube 可跑，910A 的 FP32 Vector 只有约 4T，这条会比 softmax/RMS 更早露出来。不能把 910A 说成和 H100 同一个「Vector 无所谓」区间。
- chip-simulator 那一列是 **改记账之前** 的扫：固定 H100 Cube、同拍时，**16:1 起 Prefill 的 GDN 变成 Vector 墙**；Decode 从 **8:1** 起掉 tok/s，用的是 BF16 \(2MK\)（gate 189 M vs 713 M）。GDN 这条仍然成立。Decode 那条不能直接当成现行 FP32 量化的结果；配比页上同一比例的 Decode 仍是带宽墙。
- MI355X 以前按「Vector = 2×FP32」写成 314.6T（约 8:1）。AMD 公布的 Vector FP16 就是 **157.3T**，和 FP32 一样，**Cube:Vector ≈ 16:1**。MI455X 同样是 Vector FP16 = 315T、Matrix BF16 5.03P，还是约 **16:1**。Rubin 的 CUDA FP32 是 130T，按本表惯例 Vector BF16 = 260T，对 4P Cube 约 **15:1**。2025–2026 这几颗的半精度 Cube:Vector 都堆在 16:1 附近，不是更胖的 8:1。
- B300 的 dense NVFP4 按 DGX 八卡 108P 折算是 **13.5P**，不是 15P；BF16 仍是 **2.25P**，和 B200 相同。2.5P 那列不要和这行混用。

新进行：910A、Rubin（2026）、MI455X（2026）。TPU Ironwood / Trainium3 没有可对账的 Vector 峰值，没有塞进表。

## 还答不出的

同等 **面积或功耗** 下，1 mm² 换成 Cube、Vector 还是 HBM 哪个更值。没有这笔账，就不能说「最好的配比」。下一步若要一个数，应在 chip-simulator 里固定面积（或功耗），扫 PE 几何 × SRAM × HBM × 能否同拍，看 Prefill ms 与 Decode tok/s 的帕累托。
